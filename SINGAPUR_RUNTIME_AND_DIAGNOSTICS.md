# singapur: runtime configuration and diagnostics

Updated: 2026-09-03

This note is a non-secret operational reference for the `singapur` deployment.
It intentionally excludes `.env` values, API credentials, session secrets, and
private key material.

## Runtime topology

The project-managed deployment has one long-lived `screen` session:

| Session | Service | Local endpoint |
| --- | --- | --- |
| `trading-mcp` | Bybit streamable HTTP MCP | `127.0.0.1:8791/mcp/bybit` |
| `trading-mcp` | MEXC streamable HTTP MCP | `127.0.0.1:8792/mcp/mexc` |

The project no longer runs a Web UI or a project-managed `codex app-server` on
`singapur`. In particular, `127.0.0.1:8787` and `127.0.0.1:8790` are not
expected to listen, and their former Tailscale/Funnel publication is not part
of the current topology.

Codex remote access remains available as a host-managed Codex runtime. ChatGPT
Work reaches it through SSH; it is separate from this repository's former Web
UI/app-server deployment and must not be diagnosed or restarted as `codex-app`
or `webui` project services. Tailscale Serve publishes only the MCP endpoints.

## Normal operations

Run these commands on `singapur` from `/root/projects/trading-mcp`:

```bash
npm run singapur:status
npm run singapur:mcp
bash scripts/singapur/export-runtime-config.sh
```

Do not use `npm run singapur:webui` or `npm run singapur:codex` as recovery
commands for the current production topology. Those launchers remain in the
repository for local or historical use, but do not describe active Singapur
services.

`artifacts/singapur/` is regenerated by the export script and contains separate
non-secret files for the OS/runtime inventory, Tailscale routing, public Nginx
routing directives, and the project MCP runtime defaults.

## Logging

The MCP launch wrapper writes startup stdout/stderr to:

```text
artifacts/mcp/bybit.log
artifacts/mcp/mexc.log
```

These MCP files currently contain lifecycle output only. Web UI JSONL files are
historical artifacts and are not an observability source for the active
Singapur topology. Diagnose ChatGPT Work / remote Codex behaviour through its
SSH-accessible host runtime, separately from the MCP service logs.

## Reliable diagnosis

Use the correct network vantage point before making an availability conclusion:

1. A `curl` from `singapur` to its own MagicDNS hostname is a local hairpin
   test. It does not prove how a separate tailnet client behaves.
2. `tailscale serve status --json` and `tailscale funnel status --json` show
   configured routing, not a complete end-to-end browser/TLS test.
3. Keep Nginx `server {}` blocks intact when inspecting them. A flattened grep
   of `listen`, `root`, and `server_name` directives cannot safely associate a
   route with a vhost.
4. Validate MCP client access from the actual client or a separate tailnet
   node: DNS answer, certificate/SNI, HTTP response, then MCP `tools/list` or
   a read-only tool call.
5. Diagnose ChatGPT Work's Codex session over SSH. A missing Web UI route or
   port `8790` is expected and is not an MCP incident.

## Known observations

- `trading-mcp` is the only project screen expected to be running.
- A missing local Web UI (`8787`) or project Codex app-server (`8790`) is the
  intended state, not a service failure.
- The remote Codex runtime used by ChatGPT Work is reached via SSH and is not
  published as a project WebSocket endpoint.
