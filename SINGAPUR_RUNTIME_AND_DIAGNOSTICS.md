# singapur: runtime configuration and diagnostics

Updated: 2026-08-24

This note is a non-secret operational reference for the `singapur` deployment.
It intentionally excludes `.env` values, API credentials, session secrets, and
private key material.

## Runtime topology

The deployment is split into three long-lived `screen` sessions:

| Session | Service | Local endpoint |
| --- | --- | --- |
| `trading-mcp` | Bybit streamable HTTP MCP | `127.0.0.1:8791/mcp/bybit` |
| `trading-mcp` | MEXC streamable HTTP MCP | `127.0.0.1:8792/mcp/mexc` |
| `codex-app` | Codex app-server over WebSocket | `ws://127.0.0.1:8790` |
| `webui` | Local MCP Web UI | `127.0.0.1:8787` |

The Web UI uses external Codex mode and the Codex app-server uses the two local
HTTP MCP services. Tailscale Serve publishes ports `8790`, `8791`, and `8792`
inside the tailnet. The Web UI launcher configures Tailscale Funnel and session
authentication.

## Normal operations

Run these commands on `singapur` from `/root/projects/trading-mcp`:

```bash
npm run singapur:status
npm run singapur:mcp
npm run singapur:webui
bash scripts/singapur/export-runtime-config.sh
```

`artifacts/singapur/` is regenerated by the export script and contains separate
non-secret files for the OS/runtime inventory, Tailscale routing, public Nginx
routing directives, and the project runtime defaults.

## Logging

Web UI logs are JSONL files in `apps/local-mcp-web-ui/artifacts/logs/`.
They rotate when the UTC date changes or a file reaches 10 MiB by default.
Retention defaults to 30 days and at most 100 retained files.

```text
WEB_UI_LOG_MAX_BYTES=10485760
WEB_UI_LOG_RETENTION_DAYS=30
WEB_UI_LOG_MAX_FILES=100
```

The MCP launch wrapper writes startup stdout/stderr to:

```text
artifacts/mcp/bybit.log
artifacts/mcp/mexc.log
```

These MCP files currently contain lifecycle output only. Per-request and
per-tool observability is available through the Web UI's Codex app-server event
log, not through the MCP files themselves.

## Reliable diagnosis

Use the correct network vantage point before making an availability conclusion:

1. A `curl` from `singapur` to its own MagicDNS hostname is a local hairpin
   test. It does not prove how a browser on another tailnet node or the public
   Funnel route behaves.
2. `tailscale serve status --json` and `tailscale funnel status --json` show
   configured routing, not a complete end-to-end browser/TLS test.
3. Keep Nginx `server {}` blocks intact when inspecting them. A flattened grep
   of `listen`, `root`, and `server_name` directives cannot safely associate a
   route with a vhost.
4. Validate client access from the actual browser or a separate tailnet node:
   DNS answer, certificate/SNI, HTTP response, then a fresh authenticated UI
   interaction.
5. `401` records for unauthenticated `/`, `/chatkit`, `/.env`, and `.git`
   probes are expected session-auth denials, not application failures.

  synchronization.
- Tailscale logs report an address-in-use conflict on port `443`, owned by
